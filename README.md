# Instamart Customer Intelligence and Support Copilot

## Overview

This project builds an internal Customer Intelligence and Support Copilot using synthetic and fictional Instamart-style data.

The project is divided into four connected parts:

- **Part A – Data Foundation:** Audits, cleans, stores and queries customer, product and order data.
- **Part B – Customer Intelligence:** Creates RFM customer segments, predicts customer lapse risk and produces a retention list.
- **Part C – Support Ticket Triage:** Redacts personal information, classifies support tickets, validates model outputs and routes tickets with safety guardrails.
- **Part D – Policy RAG and Refund Agent:** Retrieves policy information, answers grounded questions and executes simulated refund workflows through registered tools.

All datasets are synthetic and generated by the supplied `generate_data.py`. No real customer records, real Instamart orders, production policies or real financial transactions are used.

All model calls use the supplied offline `mock_llm.py`. The project requires no external API key, hosted model, network connection or paid service.

## Reproduce

### Requirements

- Python 3.11 or newer.
- SQLite 3.25 or newer.
- Git.
- The supplied `generate_data.py` and `mock_llm.py` files.

The project uses Python, pandas, NumPy, scikit-learn, joblib and SQLite. Install the dependencies from the committed `requirements.txt`.

### 1. Clone the repository

Replace the repository URL with the public GitHub repository URL.

```powershell
git clone https://github.com/YUgendhAR90/instamart-copilot.git
cd instamart-copilot
```

### 2. Create and activate a virtual environment

```powershell
py -m venv .venv
```

Activate it:

```powershell
.\.venv\Scripts\Activate.ps1
```

If PowerShell blocks activation, run:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
```

Then activate the environment again.

### 3. Install dependencies

```powershell
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### 4. Verify the supplied files and generate the synthetic data

The supplied files must remain unmodified.

```powershell
python -m py_compile generate_data.py mock_llm.py
```

### Task 2: Vectorization and retrieval

Fitted a scikit-learn `TfidfVectorizer` to the policy chunk texts. Queries are transformed using the same fitted vectorizer, then ranked using cosine similarity.

The reference query `refund policy late delivery` returned three chunks from `refund_policy.txt`.

TF-IDF is a lexical retrieval method. A limitation is that phrases with similar meanings but different vocabulary may receive low similarity.

### Task 3: Policy RAG assistant

The user message contains the retrieved context with source filenames and the question. The system prompt requires answers based only on supplied context and uses the required fallback when information cannot be found.

### Task 9: ReAct versus Plan-and-Execute

The implemented ReAct agent makes decisions one step at a time by observing each tool result before choosing the next action. S1 required five model calls and 1,557 tokens, S5 required three calls and 733 tokens, and S6 required two calls and 336 tokens.

A plan-and-execute agent could generate the entire tool sequence in one planning call and replan only when an unexpected observation occurs. This could reduce calls for predictable requests, but unexpected observations such as `NOT_FOUND` or a cancelled order would require replanning. ReAct uses more model calls, but we chose it because each refund action depends on verified order status, delivery time and refund eligibility.

---\n\n## Limitations & future work

### Synthetic data

All customer, product, order, ticket, policy-evaluation and agent-scenario data is synthetic and fictional. The outputs do not represent real Instamart customer behaviour, business performance or production policies.

### Offline model

All model calls use the supplied deterministic offline `mock_llm.py`. Results demonstrate the required application logic and simulated model behaviour; they are not evidence of real hosted-model accuracy or production performance.

No external API key, paid model, hosted service or network call is required.

### Customer lapse prediction

The lapse prediction features use historical data strictly before the 2025-09-01 cutoff. The train-test split is stratified and preprocessing is fitted on training rows only. Oversampling is restricted to training data, and the original test set remains unchanged.

However, the Premium customer segment is calculated using the full RFM window up to the 2025-10-01 snapshot. Its segment label is therefore a post-hoc whole-window label. It is not used as a lapse-model feature and is not a leakage-free segment available at the original September prediction cutoff.

Consequently, the Premium retention list is illustrative rather than a leakage-free evaluation of a deployable retention campaign. In the selected top ten test-set Premium customers, zero were actually lapsed.

### Ticket privacy

The redaction stage covers the email, Indian ten-digit phone-number and order-ID patterns defined in the assignment. Other possible personal-information formats would require additional detection and redaction rules before production deployment.

### Policy retrieval

TF-IDF and cosine similarity use lexical overlap, not deep semantic understanding. Policy questions using synonyms or substantially different wording may require additional retrieval techniques and manual review.

### Refund actions

The refund ledger records simulated issuance and escalation events only. No actual money is transferred and no production payment gateway is connected.

### Future improvements

Potential next steps include testing a real, securely hosted language model, stronger semantic retrieval, broader personal-information detection, production monitoring, human approval interfaces, idempotent financial transactions and a temporally valid Premium-segment definition for operational retention campaigns.
